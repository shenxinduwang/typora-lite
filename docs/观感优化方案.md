# typora-lite 阅读区观感优化方案（草案 v1）

> 目标：把编辑区的"展示效果"拉到接近 ima 阅读器的水准。
> 本文只做方案，不含代码。最后有三件需要拍板的事。
> 分析依据：两张截图（typora-lite / ima 打开同一份 Spring Boot 笔记）+ 仓库源码（`src/liveMarkdown.js`、`src/style.css`、`src/main.js`、`src/outline.js`）+ 截图像素实测。

## 2. 为什么差这么多：两条结构性原因

### 原因一：装饰模型的层级选得偏低

CodeMirror 三种装饰能画的东西是硬边界，不是调 CSS 能突破的：

| 装饰类型 | 作用对象 | 能画 | 画不了 |
|---|---|---|---|
| `Decoration.mark` | 一段**文本 range** | 字体、颜色、**只覆盖文字 run 的背景** | 整行背景、内边距、圆角、边框 |
| `Decoration.line` | **整行**（`.cm-line` div） | 整行背景、左右内边距、上下 padding、边框 | 跨行的连续容器（要逐行拼）、横向滚动区 |
| `Decoration.replace`（block widget） | **整段 range**（须对齐行边界） | 任意 DOM：真 `<pre>`、真 `<table>`、按钮 | 块内直接编辑（要退出 widget 才能编辑） |

现状是：代码块和表格都在用 `mark`（最低一级），所以它们**结构上不可能**长得像 ima——背景贴着字走，容器、圆角、内边距、复制按钮全都长不出来。这不是样式没调好，是层级选错了。

标题、引用用的是 `line`，所以它们能做对；图片用了 `replace` 但没开 `block`，所以能显示但拿不到块级布局。

### 原因二：视觉参数从没标定过

列宽 760px、左右 padding 0、行高 1.7、`marginTop` 当行间距、`#fbfbfb` 当内容底色——这些是"能跑起来"的工程默认值，没有一个是对着目标观感定过的。ima 的每一处都是定过的：32px 栏内留白、41px 头部条、`#F6F6F6` 头 vs `#FFFFFF` 体、`#EBEBEB` 描边、圆角、正文与容器的双重留白。

## 3. 方案：分三层推进

### L0 参数标定（纯 CSS，零功能风险）

1. **内容列留白**：`.cm-content` 的 `padding: 20px 0 60vh 0` → `padding: 28px 32px 60vh`；`#editor .cm-editor` 的 `max-width` 760px → 820px。
   - 安全：CM 的 `lineWrapping` 与 `posAtCoords` 都走同一个盒模型，padding 是被正确计入的。
   - 保留 `60vh` 底部 padding——那是"最后一行能滚到顶"的 Typora 技巧，别删。

2. **字体栈**：正文改 `"Segoe UI Variable Text", "Segoe UI", system-ui, -apple-system, "PingFang SC", "HarmonyOS Sans SC", "Microsoft YaHei UI", "Microsoft YaHei", sans-serif`；等宽改 `"Cascadia Mono", ui-monospace, Consolas, "Sarasa Mono SC", "JetBrains Mono", monospace`。顺手删掉 `-webkit-font-smoothing: antialiased`（Windows 上是空操作，留着只会让人以为生效了）。

3. **垂直节奏**：
   - `.cm-h1/.cm-h2/.cm-h3` 的 `marginTop` 全部改成 `padding`。**理由**：CM 用元素矩形高度量行高，而 margin 不计入矩形高度——标题越多，累计偏移越大，会出现点击定位漂移、滚动条高度不准。现在 `.cm-h1{marginTop:.6em}`、`.cm-h2{marginTop:.5em}` 就是这个写法。
     建议值：`.cm-h1{padding:.9em 0 .3em}`、`.cm-h2{padding:.75em 0 .25em}`、`.cm-h3{padding:.6em 0 .2em}`、h4/h5/h6 用 `.5em 0 .15em`。
   - 间距收紧（从 2.73 倍 → 逼近 2.0 倍）**先只动一个旋钮**：`line-height` 1.7 → 1.65，截图对比后再决定要不要把"标题后紧跟的空行"压成半行。一次改多个旋钮，出了问题分不清是哪个。
   - 标题相对字号建议从 `1.6em/1.3em` 收到 `1.5em/1.25em`，向 ima 靠。这条主观性强，可以不做。

4. **列表符字形**：复用现有的 TaskBoxWidget 模式新增 `BulletWidget`——光标不在本列表项内时，把 `-`/`*`/`+` 折叠成 widget 画 `•`，层级由 `ListItem` 祖先深度决定（`•`→`◦`→`▪`）；有序列表保留数字，但加 `font-variant-numeric: tabular-nums` 并右对齐。
   - 已知副作用：折叠后点击"列表符左侧"会落到行首——与 Typora 行为一致，可接受。

5. **区域色**：内容区 `#FFFFFF`，侧栏保持浅灰，靠色差区分区域，而不是靠内容区自己变灰。

6. **大纲面板**：
   - `white-space: nowrap` → 允许两行（`display:-webkit-box; -webkit-line-clamp:2`），长度不再被吃掉。
   - `.ol-l1..l6` 的 `padding-left` 硬编码改成层级变量 + `::before` 画 1px 竖线，做出缩进引导线。
   - 宽度 240px → 260px。

7. **顶栏**：7 个描边按钮 → 无边框 SVG 图标按钮（hover 才出底色），按"文件 / 视图"分组，"自动保存"和"主题"收进一个下拉菜单；文件名移到顶部居中。

8. **图片/行内代码/引用**的微调：图片 `margin: 8px auto` 居中、`border-radius: 8px`、`max-height` 提到 480px；行内代码 `padding: 2px 5px`、`font-size: .92em`；引用块补一层浅背景。

### L1 结构性补齐（要改装饰模型）

**9. 代码块容器 —— 最大的一处，也是唯一必须做路线选择的一处。**

先看现状为什么长不出来：`liveMarkdown.js:242-243` 用 `Decoration.mark({class:"cm-codeblock"})` 盖住整个 `FencedCode` 节点，CSS 只给 `background-color`。mark 只能覆盖文字 run，所以实测背景严格贴着字形，同一行的空白处就掉回页面底色。**容器、圆角、内边距、头部条、复制按钮，在 mark 这个层级上一个都做不出来。**

两条路线：

**路线 A｜逐行 line 装饰拼容器**（保留"光标进块即编辑"）

- `FencedCode` 内每行加 `Decoration.line('cm-cb')`，首行 `cm-cb-first`、末行 `cm-cb-last` 负责圆角
- 左右用 `.cm-line` 的 padding 撑开，上下给首行 `padding-top` / 末行 `padding-bottom`（CM 对 line 的 padding 支持良好）
- 语言标签用首行的 `::after`
- 「复制」按钮不能放在行内（会被 scroller 裁），用**编辑器容器上的绝对定位按钮**，监听 mousemove / 滚动，定位到当前 hover 的代码块首行右侧
- 拿不到的：①长代码行仍随 `lineWrapping` 折行，做不出 `overflow-x: auto`；②按钮定位要多一层逻辑
- 改动面：`liveMarkdown.js` 的 `FencedCode` 分支 + CSS
- 工作量：小。观感能拿到 ima 的 **约 80%**

**路线 B｜阅读态 block widget**（观感可以做到 1:1）

- 光标不在 fence 内时，`Decoration.replace({block:true, widget})` 把整段换成真 `<pre><code>` 容器（头部条 + 语言标签 + 复制按钮 + 圆角 + 描边 + 横向滚动）；光标进入时撤掉 widget，回到原文编辑
- 高亮：`highlightTree` 配合 `@lezer/*` 语法树 + 自定 HighlightStyle，或先做单色
- 必须处理：①点 widget 要手动把 selection 设到 fence 内，否则光标进不去；②`atomicRanges` + `ignoreEvent`；③block widget 的 range 必须对齐行边界（`FencedCode` 天然满足）；④撤销栈与中文 IME 的边界；⑤复制要走剪贴板 API，Tauri WebView2 下可能需要 `@tauri-apps/plugin-clipboard-manager`（需先确认 secure context 下原生 API 可用）
- 工作量：**A 的 3–5 倍**，且必须专门测"编辑态 ↔ 阅读态"切换

**推荐：先做 A。** A 拿到 80% 观感且完全不碰编辑模型；等你确认要做"阅读优先"，再把 A 的 CSS 直接复用到 B 的 widget 上，不浪费。

**10. 表格**：现有实现（表头加粗 + 分隔行折叠 + 竖线弱化）在路线 A 下最多做到"有框线的文本矩阵"——因为 `|` 是正文文本字符，列宽由内容决定，CJK 混排下根本对不齐。**真表格只能靠 block widget**，所以表格是路线 B 的甜点区，本阶段不动。

**11. 大纲折叠**：`outline.js` 现在只返回扁平的 `{level,text,from}`，`main.js` 平铺 DOM。要折叠得先在 JS 里建父子关系树（按 level 降序压栈），再渲染成可折叠节点 + 根节点（文档名）。不碰编辑模型，中等工作量。

### L2 可选项（暂不做）

- 代码块语言标签、横向滚动（依赖 B）
- 图片点击放大
- 引用块背景与嵌套样式

## 3.5 「阅读 / 编辑模式」开关：不建议做（2026-09-15 定）

### README 里的既有立场

项目自己的三条表述已经给出答案：

- `README.md:3` — 定位是「对标 Typora『所见即所得 / 打字即渲染』体验，但体积更小、冷启动更快、纯 Windows 原生」。
- `README.md:120` — 把「双栏预览模式」明确列为**与 lite 体积定位有张力**、建议单独立项。
- `README.md:107,112` — 核心机制是「Typora 式原地渲染」「光标聚焦才显示标记」，全篇只有**一个**心智模型：单栏、无模式。

「阅读 / 编辑」开关会把这个唯一卖点换成二选一。对 2.6MB 的安装包，用户第一次打开要先决定「我该用哪个模式」——这是学习成本，不是功能。

### 它省不掉 B 路线真正的难点

模式开关能省的只有一处：阅读态下不会切回原文，所以不用写「点击 widget 后把光标塞进 fence 内」。剩下的全都得做：

- block widget 的 range 对齐、`atomicRanges`、`ignoreEvent`
- 容器高度 ≠ 原文行高，两态切换时的布局跳变与滚动位置换算
- 光标位置在「字符偏移」与「容器内」之间互转
- 复制按钮、剪贴板权限、语言标签
- 高亮要单独跑一遍 `highlightTree`

而且它**新增一个正交状态位**：模式 × 脏标记 × 30s 自动保存 × 3s 外部修改监听 × 崩溃草稿恢复 × 关窗拦截 × 最近文件恢复。README 第 86、93、94、95 行整段都在讲这些状态机，而 v0.2.0 → 0.2.3 四轮评审修的基本全是状态竞态——这个项目的成本中心在状态机，不在渲染。加一个状态位，测试面是翻倍，不是加一。

### 替代方案：沿用项目已有的 `caretIn` 模式，零新概念

`liveMarkdown.js:198` 的 `caretIn(a, b)` 已经在驱动标题标记、行内代码标记、图片、任务框、表格分隔行、分割线——「光标不在范围内就渲染，进去就显示原文」。代码块容器用同一个判断即可：

- 光标不在这个 `FencedCode` 内 → 替换成 block widget（圆角容器 + 头部条 + 复制 + 高亮）
- 光标进入 → 撤销 widget，回到原文编辑

这就是 Typora 本来的行为（Typora 的代码块同样是进入后才显示 ``` 与源码），不需要新模式。

**这条路的唯一硬骨头**：点击进入时会有一帧布局跳变（容器有内边距、原文没有），CM 把点击坐标重映射后落点可能不准。缓解做法——容器的上下内边距按「半行行高」设计而非固定 16px，把跳变压小；点击时用 `posAtCoords` 反查位置后手动 `setSelection`，不依赖 CM 默认映射。必须实测。

### 如果最终还是想要一个开关，做「只读」而不是「阅读」

最轻的形态是一个布尔：`EditorState.readOnly.of(true)` + `EditorView.editable.of(false)`，塞进 `Compartment`。语义是「我暂时不改它」，**渲染逻辑一行都不用动**——只读态下可以放心全量渲染 block widget，不用管回落。它不引入第二套渲染器。但与「打字即渲染」的定位仍有张力，所以排在 L2。

### 附带发现

README `README.md:119` 已把「表格渲染成真 `<table>` 交互」列为后续目标——**block widget 本来就在这个项目的路线图里**，不是模式开关带来的新东西。

## 5. 怎么证明改对了

1. **基准文档**：就用截图里那份 Spring Boot 笔记。改前改后各截一张**同窗口宽度、同 DPR** 的图做叠差。跨 DPR 比对没有意义。
2. **可量化断言**（这条最有用）：代码块必须在"同一行的空白处"也有背景色。现状实测空白处是 `(251,251,251)`，改对了应该恒定等于容器底色。可以直接写个像素检查脚本卡这一条。
3. **CM 特有风险的必测项**（每次改完手测一遍，这四项是这类改动的雷区）：
   - 文末位置点击，光标落点是否与视觉一致（验证 P0-3 是否真的修掉了行高漂移）
   - 中文 IME 长文档输入，候选框位置与断词
   - 滚到底部是否还有 `60vh` 的空白可滚
   - 路线 A 下代码块内是否仍能直接打字（这是 A 相对 B 的唯一优势，破了就没意义了）
4. **每项单独提交**，出问题可以二分回退。

---

## 6. 需要拍板的两件事

1. **代码块走 A 还是 B？** A = 逐行 line 装饰拼容器、编辑优先、约 80% 观感、改动小；B = 阅读态 block widget、1:1 观感、3–5 倍工作量，必须处理块内编辑回落与点击落点。
2. **标题—正文间距要不要收到 ima 的水平？** 会改变现有的阅读节奏感，且这条主观性最强。

「阅读 / 编辑模式」开关已单独在第 3.5 节定调：不建议做，改用 `caretIn` 同构的「聚焦即编辑」。

我的建议：1 选 A，2 先只动 line-height 看效果。

## 7. 改动顺序（按依赖与收益排序）

1. **L0 全部**（P0-1 ~ P0-9）——与路线选择无关，无论走 A 还是 B 都要做，且收益立即可见。风险最低，先落地。
2. **P1-1 代码块容器（路线 A）**——拿到容器感、圆角、内边距。
3. **P1-2 复制按钮**——A 路线下按钮是 overlay，需要先确认剪贴板方案。
4. **P1-3 大纲折叠树**——独立，可并行。
5. **评估要不要把 P1-1 换成 B 的 widget**——此时 A 的 CSS 可直接复用。
